# `valos.json` — machine-readable dataset (experimental)

> **Status: experimental.** The structure may change without notice while the
> data-separated source format settles. Do not build load-bearing integrations
> against it yet; feedback on the shape is welcome via issues.

Every deployment publishes `valos.json` next to the spec
(`https://lidofinance.github.io/valos/valos.json`). It is generated by
`scripts/build.mjs` from the same validated sources as the specification
itself (`risks/`, `controls/`, `mitigations/`), so it can never drift from
the published document.

## Shape

```jsonc
{
  "$schema": "experimental — structure may change without notice",
  "source": "https://lidofinance.github.io/valos/valos-spec.html",
  "publishDate": "2026-07-10",

  // one entry per risk row, including retired identifiers
  "risks": [
    {
      "id": "FIN1",
      "href": "#risk-fin-1",           // anchor in the published spec
      "category": "sec-risks-financial",
      "group": "Process",
      "vector": "Onboarding",
      "description": "…"
      // retired entries have "retired": "<explanation>" instead of
      // group/vector/description; consolidations carry "replaces": ["SLS8", …]
    }
  ],

  // one entry per mitigation section
  "mitigations": [
    {
      "id": "sec-mit-client-diversity",
      "title": "Client Diversity",
      "links": [
        // OSCAL-style typed relationship links; one declared direction
        // (mitigation → risk); build reverse indexes yourself as needed
        { "rel": "mitigates", "riskId": "SLS6", "href": "#risk-sls-6" },
        { "rel": "mitigates", "scope": "category", "href": "#sec-risks-keys" },
        { "rel": "mitigates", "scope": "all-risks" }
      ]
    }
  ],

  // one entry per requirement (a control heading can carry several)
  "controls": [
    {
      "id": "req-manage-keys",
      "href": "#req-manage-keys",
      "section": "sec-controls-info-secrets",
      "title": "Key Management",
      "statement": "Node Operators MUST implement appropriate key management procedures",
      "links": [
        { "rel": "addresses", "riskId": "HCK1", "href": "#risk-hck-1" },
        { "rel": "addresses", "scope": "all-risks" },
        { "rel": "maps-to", "standard": "SOC2", "control": "CC 5.2" }
      ]
    }
  ]
}
```

## Conventions

- **Stable ids** are the same ones the spec's anchors use (`FIN1` ↔
  `#risk-fin-1`, `req-*`, `sec-mit-*`). They are maintained by hand in the
  source data and never derived from titles.
- **Relationships are `links` arrays with `rel` tokens** (`mitigates`,
  `addresses`, `maps-to`), following the convention of
  [NIST OSCAL](https://pages.nist.gov/OSCAL/): one declared direction per
  relation, uniform shape, extensible with further fields (e.g. a mapping
  relationship type) without breaking consumers.
- **External standard mappings** (`rel: "maps-to"`) currently cover SOC2 and
  ISO27001 references as written in the spec's info boxes.
